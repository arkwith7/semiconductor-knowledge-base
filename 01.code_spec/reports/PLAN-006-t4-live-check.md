## 2. 표본 24 검색식 (dev b·d 로그 · 시드 20261012 · 층화)

층: 채택 6 · 예산 초과 거부 4 · 0건 3 · 구문 3 · NOT 2 · 영어 포함 3 · IPC 한정 3.

- **건수 규모:** 라이브 청구항 한정 총건수는 로컬 결과의 중앙값 **13.8 배**, 라이브 `word` 는 청구항 한정의 중앙값 **24.9 배**다.
  → **로컬에서 검토량 200 안에 들던 검색식이 라이브에서는 수천~수십만 건**이 된다. 로컬 평가의 검토량은 라이브 검토량으로 옮겨지지 않는다.
- **교차 비교:** 라이브 결과를 전부 받을 수 있었던(총건수 ≤ 1,500) 6 검색식만 로컬 코퍼스와 교차했다.
  - 큰 불일치 2건의 원인은 **IPC 파라미터**다 — 로컬은 IPC 3·5개를 OR + 판 대응(H01L↔H10)으로 확장했는데 라이브에는 첫 코드만 보냈다.
    로컬 KR 문헌 86 중 85, 190 중 140 이 "첫 코드가 아닌 코드나 판 대응 코드로만" 걸린 문헌이었고, 그 수가 라이브 누락과 맞는다.
  - **잔여 불일치:** 8건(2번째 IPC 검색식)과 4건(단일 IPC `G03F1` 검색식) — 형태소·구문 처리나 현재 IPC 차이로 추정(개별 확인 전 · 가정).
  - 반대 방향 — 라이브가 찾았으나 로컬이 못 찾은 코퍼스 문헌(16·43·361·100건) — 대부분 **상세한 설명에서만 맞는 문헌**으로 추정(라이브 `word` 범위).
- **0건 검색식 3:** 라이브에서는 0건이 아니다(50 · 15,855 · 182,591) — 같은 이유(전문 범위·전체 DB).
- **로컬 크기 +1:** 로그의 결과 수는 질의 문서 자신을 뺀 값이고 이번 재실행은 빼지 않아 1 차이가 난다(구현 차이 아님).

## 3. 결론과 기록

1. **연산자 의미(AND·OR·NOT·괄호·공백)는 라이브와 같다.** 검색식의 논리 구조는 그대로 옮겨진다.
2. **세 가지가 다르다 — 모두 한계로 기록한다:** (a) 라이브 자유 검색은 상세한 설명까지 본다 (b) 한글은 형태소 정규화, 구문 검색은 훨씬 엄격하다 (c) API 의 IPC 는 한 코드·판 대응 없음.
3. **T4 v1 의 해석 범위:** dev 결과는 "제목·초록·청구항 범위의 동결 코퍼스에서의 선별력" 이다. **라이브 KIPRIS 에서 같은 검토량으로 같은 회수가 나온다고 쓰지 않는다.**
4. 실사용(A사 등)으로 옮길 때 필요한 것: 라이브 필드 한정(청구항·초록) 조합 방식, IPC 다중 코드·판 대응 처리, 라이브 검토량 상한 재설정 — **설계 안건으로만 등재**(이번에 바꾸지 않음).
