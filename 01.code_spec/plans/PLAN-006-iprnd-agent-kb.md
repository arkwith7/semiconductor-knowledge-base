## 0. 결론 먼저

**지금 그래프는 T1 에 치우쳐 있고, T4 는 부품만 있으며, T2·T3 는 원천 데이터부터 없다.**
그래서 순서는 **T4(구조화 검색식) → 에이전트 인터페이스 → T2(FTO) → T3(신규 특허 도출)** 이다.
T4 가 먼저인 이유는 셋이다 — ① 목적 문장의 "충분한 결과물" 기준이 바로 그것이고 ② **외부 정답이
이미 있다**(SIRP 심사관 인용문헌의 회수) ③ T2·T3 도 결국 검색식으로 모집단을 끌어온다.

**PLAN-005 의 원 요구에 FTO 가 있었다**(PLAN-005 머리말 *"신규성·진보성·FTO 라는 명확한 업무
목적"*). 그것이 PLAN-005 §7 에서 비목표로 빠졌고, 그 뒤 작업은 T1 회수와 논증층 정밀도에
집중됐다. 이 계획은 그 빠진 목적을 되돌려 놓는다.

### 3.1 단계 1 — T4 (요지 · 설계는 §2 3단계에서)

- **정답:** SIRP **dev** 출원의 **심사관 인용문헌**. 생성한 검색식을 실행해 회수되는지 잰다.
  검색식 문자열 정답은 없다 — 수집자 seed 검색식(`meta.search_query`)은 심사관 것이 아니므로
  **정답이 아니라 비교군 (a)** 다.
- **실행 환경 (2026-10-09 사용자 결정):** 주 판정 = **로컬 후보 코퍼스에서 KIPRIS 문법 에뮬레이션**
  (재현성) · 라이브 KIPRIS `getAdvancedSearch` 는 표본 일치 확인용.
- **비교군:** (a) 수집자 seed 검색식 (b) LLM 단독 (c) 온톨로지 고정 절차 (d) LLM + 온톨로지 도구.
  호출 수·토큰을 함께 기록한다. **d ≈ b 면 온톨로지의 추가 효용을 재검토하고 그대로 보고한다.**
- **LLM 범위 (2026-10-09 사용자 결정):** 입력은 **공개 청구항·초록뿐**. 통지서·결정서 원문은
  보내지 않는다(§1-5 개인정보). LLM 산출물은 동결하고 sha256 과 함께 커밋한다(PLAN-005 V4 선례).
- **판단지식 재사용:** **train** 출원의 심사관 판단(요소 ↔ 문헌)에서 어느 개념 패싯·IPC 가
  인용문헌을 맞혔는지를 집계해 패싯 가중으로 쓴다 — PLAN-005 §20.3 G-1 *"판단지식 재사용이
  실험된 적이 없다"* 의 첫 시험이다.
- **어휘:** 새 모듈(가칭 `sdkb-search.ttl`) — core·semi·kr 은 sha 동결(PLAN-005 V6b)이므로
  기존 모듈을 건드리지 않는다. 별도 승인.
- **계측 규율:** PLAN-005 R0 교정 계측기 · `split.csv` 714dafe0… · dev 주 판정 · test/test_b 봉인.

### 3.1′ 단계 1 요구 정의 — 승인 조건 (2026-10-09 · 사용자 승인)

**요구 정의는 아래 조건을 붙여 승인됐다.** 위 3.1 과 충돌하면 이 절이 우선한다.

1. **주 비교는 d 대 b**(LLM+온톨로지 대 LLM 단독)다. c 대 a 는 고정 절차가 유효한지 확인하는 비교다.
   d ≈ b 이면 결론은 성능 우월이 아니라 **근거 추적성·검색식 통제 가능성** 쪽으로 조정한다. 결과와 무관하게 본문에서 보고한다.
2. **검토 부담은 두 방향으로 보고한다.** (i) 고정 검토량에서의 회수율 (ii) 목표 회수율에 도달하는 데 필요한 결과 집합 크기.
3. **Boolean 결과에는 순위가 없다.** 상한 초과 시의 처리(실패 처리 또는 사전 정의된 완화·축소 절차)를 3단계에서 정한다.
   순위화해 상위만 평가하는 방식은 검색식 효과와 랭커 효과를 섞으므로 주 판정에 쓰지 않는다.
4. **분모 두 개를 병기한다.** 전체 정답 대비 회수율과 코퍼스 안에서 회수 가능한 정답 대비 회수율. 제외 사유(코퍼스 밖·검색 필드 없음·일본어 등)를 따로 남긴다.
5. **dev 는 개발용이다.** dev 는 어휘 채굴(harvest 범위 dev+train 800)·분석·사람 검증에 이미 쓰였다. dev 결과는 "개발 단계 효과 확인"으로만 서술하고,
   **일반화 근거는 생성기 동결 후 A사 미사용 사례**에서 얻는다.
6. **검토량 상한과 문턱은 업무상 검토 가능한 양과 train 분석으로 정한다.** 2단계에서 비교군별 dev 성능을 산출하지 않는다 — dev 비교는 문턱 동결 뒤에만 낸다.
7. **어블레이션:** c 를 (c1) 별칭·동의어만 (c2) + 개념↔IPC 연결 (c3) + train 판단 기반 패싯 가중으로 나눠 비교한다.
   IPC 는 **한정 없음 · 엄격 한정 · 완화 한정**을 함께 분석한다.
8. **코퍼스 (가):** 하류의 기존 코퍼스를 출처가 기록된 **동결 스냅샷**으로 상류에 이관하고, 이후 생성·정규화·버전 관리는 **상류 단독**이 맡는다. 하류는 승인된 버전을 참조한다.
   매니페스트: 파일 해시 · 출처 커밋 · 생성 코드 버전 · 수집 범위 · 필드 정의 · 식별자 정규화 · 중복 처리 · 분할 정보.
9. **코퍼스 구성의 해석 한계 (2026-10-09 확인 · 하류 SPEC-007).** 후보 41,031 = 거절 질의 1,008 · 인용문헌 3,513 · **g1 삼성·SK하이닉스 출원 24,173** · **g2 KSIA 소부장 188사 출원 12,337**.
   출원인 기준 표집이지 seed 검색식 산출물이 아니다. 다만 **서지가 확보된 인용문헌 3,513 은 구성상 코퍼스에 들어 있다**(dev 14 · train 64 쌍의 문헌은 미수록 — 2단계 리포트 §1 정정). 결과는 "이 동결 코퍼스 안에서의 효율"로 한정해 해석한다.
10. **2단계 핵심 산출물**은 자산 수량표가 아니라 **출원 사례별 비교표**다: 입력 → 개념 접지 → 검색식 → 회수·누락 문헌 → 검토량 변화.

**A사 수집 조건:** 출원인명 부분일치는 후보 탐색에만 쓴다. 정확한 법인명·과거 명칭·출원인 코드·공동출원으로 모집단을 확정한다.
경쟁 영역은 **IPC + 기술개념 + 제품·공정 용도**로 정의한다. 사례는 생성기 동결 후 적용하며, 공개 청구항 입력과 함께 **짧은 기술 설명 입력**에도 적용한다.
실명은 비공개 원천에만 두되 경로만으로 비공개가 보장되지 않으므로, 공개 발행 허용목록 밖·리포트·로그 비노출을 **검사로** 막는다(3단계 설계).

- **주 지표:** 검토량 200(중복 제거)에서의 회수율 — 분모 셋 병기(비NPL 533 · 해소 519 · 텍스트 있음 502). 함께 **검색 성공률**(S5 후에도 200 초과 = 실패) · **집합 크기** · **성공 질의만의 회수율**을 분리 보고. 보조: 100 · 500 · 목표 회수(질의당 정답 ≥1 회수)에 필요한 집합 크기.

- **어블레이션:** c1 → c2 → c3 · IPC 없음/엄격/완화 — 서술(판정 없음).

- test·test_b 는 이번 범위에서 열지 않는다.

### 3.3′ 단계 1 설계 — 승인 조건 (2026-10-09 · 사용자 승인)

§3.3 과 충돌하면 이 절이 우선한다.

- **하류 표현 정정.** "vendor 갱신 없음" ≠ "하류 조치 없음". 그래프는 그대로지만, 하류가 이 결과를 쓰려면 **코퍼스·검색기·대응표·평가 설정의 버전 묶음**을 함께 받아야 한다 → 리포트 JSON 머리에 `bundle`(코퍼스 sha · 대응표 sha · 생성기 커밋 · 설정 sha)을 싣는다.
- **A1 코퍼스.** git 밖의 **지속 보관 위치**에 둔다. 매니페스트: 보관 위치 · 접근 방법 · 출처 커밋 · 스키마 · 행 수 · SHA-256. **파일이 없거나 해시가 다르면 실행 중단.** 내려받기·검증 절차를 제공한다. 열을 줄인 사본은 원본과 다른 **파생 평가 코퍼스**이므로 만들면 생성 스크립트·별도 해시를 둔다.
- **A2 대응표.** 공식 출처 · 분류 버전 · 원본 해시 · 변환 규칙을 기록한다.
- **A3 LLM.** SDK 버전 · 모델 · **effort** · 출력 토큰 상한 · 호출 예산을 고정하고, **실제 API 호출로 지원 설정을 확인**한다. 온도 0 을 재현성 보증으로 쓰지 않는다 — 재현성은 **산출물 동결**로 얻는다. b·d 동일: 기본 프롬프트 · 모델·사고 수준 · 토큰 상한 · 집합 크기 확인 횟수 · 검색식 수정 횟수 · 오류 재시도 · 최종 검색식 선택 규칙. **d 에만** 온톨로지 도구. API 키는 실행 환경에만(채팅 전달 금지). 키 없이도 S1–S5 · a′ · c 는 진행한다.
- **A4 판정.** **주 지표 = 검토량 200 에서의 질의별 회수율 평균(macro)** · 쌍 기준(micro)은 보조 병기 · 출원 단위 paired bootstrap.
  **주 비교 = d 대 b** 하나. **보조 비교 = 최종 c 구성 대 a′**. "최종 c 구성"은 **c3 로 사전 지정**한다 — c1–c3 중 dev 최고를 사후 선택하지 않는다.
  CI 하한 > 0 은 **통계적 개선** 판정이며 **업무상 유용성**(절대 회수율 · 검토량 · 실패율 · 비용·시간)과 분리해 보고한다. 보조 비교는 주 판정이 아니므로 다중 비교 보정을 두지 않고, 그 사실을 리포트에 적는다.
- **A5 축소·완화 절차(수정).**
  1. 집합 > 예산 → 핵심 요소 AND 추가 → 필요하면 IPC 강화.
  2. 집합 = 0 **또는 train 에서 정한 소수 결과 조건** → 주변 요소 완화.
  3. 핵심 요소를 보존한 **대안 검색식**을 제한 횟수 안에서 탐색.
  4. **최종 선택 규칙은 사전 고정** — 예산 안 여부 → 핵심 요소 충족 수 → (동률이면) 결과 수가 예산에 더 가까운 쪽. 정답을 보지 않는다. 결과 수가 많다는 이유만으로 좋은 검색식으로 보지 않는다.
  - 상한 **6 = 초기 검색 포함 총 실행 횟수**. 이미 실행한 검색식은 다시 실행하지 않는다(좁힘·완화 순환 방지). 탐색 이력을 리포트에 남긴다.
  - 보조 예산 100 · 500 은 **각 예산으로 같은 정책을 다시 실행**한다.
- **S3 에뮬레이터 명세(보강).** 괄호 · 연산자 우선순위 · 구문 검색 · **한글 부분일치** · 검색 필드 범위를 명시한다. 라이브 KIPRIS 표본과 차이를 측정해 보고한다 — 불명확하면 검색식 효과가 아니라 문자열 처리 효과를 재게 된다.
- **우선순위:** 개념 추가보다 **구체 요소를 보존하면서 너무 좁거나 넓은 검색식을 조정하는 절차**를 먼저 제대로 만든다.

### 3.4 c 재설계 — 범위와 종료 조건 (2026-10-10 · 사용자 승인)

**"c 가 a′ 를 넘을 때까지 수정" 하지 않는다.** 흐름은 원인 확인 → 제한된 재설계 → 설정 동결 → dev 평가이며, **우열과 관계없이 dev 로 간다.**

1. **원인 확인 (train · 지금):** (i) 원 표현 검색식은 예산 안이었는데 동의어·번역 추가로 초과했는가 (ii) 초과 검색식을 버리면서 이미 찾은 정답도 잃었는가
   (iii) 정답 언어(ko·en·ja)별 회수 — R2·c1 원인 분석의 핵심이라 dev 로 미루지 않는다 (iv) 예산 500 의 c1 역전이 통계적으로 확인되는가.
2. **재설계 범위 (이것만):**
   - **공통 적응 확장 정책** — 원 표현 결과를 먼저 확보 → 확장을 제한적으로 더해 **새로 들어오는 문헌 수** 확인 → **전체 합집합 기준** 잔여 예산을 넘으면 확장 취소·축소, 기존 결과는 보존. 확장 순서·최대 횟수·후보 선택 규칙은 train 에서 고정. 번역 확장은 a′·c 공통 정책, c 의 온톨로지 동의어는 별도 효과로 측정.
   - **공통 패싯 추출 개선**(더 구체적인 대표 표현)은 a′·c 모두에 적용 — c 에만 유리하게 쓰지 않는다.
   - **c2**(개념↔IPC) — IPC 를 강제 AND 로 붙여 정답을 다시 탈락시키지 않는다(넓은 검색식을 좁히는 데만 · 판 정규화는 공통).
   - **c3**(심사관 판단 기반 요소 우선순위) — train 안에서도 **출원·패밀리 단위로 학습·점검 구간을 분리**해 낙관 편향을 막는다.
3. **비교 순서:** a′ + 공통 정책 → c1 + 공통 정책(온톨로지 동의어 추가 효과) → + c2(개념↔IPC 추가 효과) → + c3(판단 우선순위 추가 효과). 각 단계는 앞 단계 대비 한 기능만 더한다.
4. **종료:** 위 범위를 train 에서 한 번 구현·측정한 뒤 설정을 동결하고 dev 를 연다. 추가 반복은 없다.
5. **"근거 추적성" 결론은 자동 전환이 아니다.** 주장하려면 별도 평가가 필요하다 — 검색 항↔원문 요소 연결 정확도 · 개념 연결 정확도 · 사용자의 검색식 수정 시간 등. IRI 를 붙였다는 사실만으로 설명 유용성이 입증되지 않는다.
6. **Bedrock 기록:** 확인된 경로(bedrock-runtime · `global.anthropic.claude-opus-5-5` · ap-northeast-2 · IAM 사용자 키 체인 · anthropic 1.12.1)를 유지하고 동결 기록에 요청 모델·프로파일·리전·SDK·응답 모델을 남긴다.

### 3.2 사례 트랙 — 실제 기업 하나로 T1–T4 를 끝까지 (2026-10-09 사용자 제안)

**왜.** IP-R&D 의 실제 업무 단위는 *한 기업의 포트폴리오와 그 경쟁 환경* 이다. SIRP 정량 평가는
"검색식이 인용문헌을 회수하는가"를 재지만, **T2·T3 는 기업 맥락 없이는 질문 자체가 서지 않는다.**
사례 트랙은 정량 평가를 **대체하지 않고 병행**한다 — 정량 평가가 방법의 일반성을, 사례가 업무
적합성을 보인다.

**대상:** 국내 반도체 소부장 장비업체 1곳 — 이하 **A사**(사용자 제안 · 익명화 결정). **현재 데이터에 이 기업 출원은 0건**
(2026-10-09 grep · 이름 일치 8건은 전부 외국인 발명자 성명) → **KIPRIS 신규 수집이 선행한다.**

| 용도 | 사례에서 하는 일 | 정답·확인 |
|---|---|---|
| 수집 | 출원인 기준 전 출원(등록·거절·공개) + 서지·청구항·법적상태·인용문헌 · IPC 분포로 경쟁 영역 정의 → 그 영역 경쟁사 등록·존속 특허 | CLAUDE.md §5 프로파일 의무 |
| T4 | 기업 출원 청구항을 아이디어로 보고 검색식 생성 → 그 출원의 **심사관 인용문헌 회수** | SIRP 와 같은 정답 형식 · 사례 단위 홀드아웃 |
| T1 | 기업 출원별 요소 단위 선행 개시 후보 + 판단 근거 | 심사관 인용 · 거절 이유가 있으면 통지서 |
| T2 | 기업 등록특허의 실시 형태(청구항 기준)를 경쟁사 **존속** 독립항과 요소 대비 | 공개 정답 없음 → **전문가 표본 판정**(정답 설계는 단계 3 의 1단계에서) |
| T3 | **역사 백테스트:** 연도 Y 이전 데이터만으로 공백·조합 후보를 내고, 그 기업이 Y 이후 실제로 출원한 기술과 대조 | 기업의 Y 이후 출원 = 사후 정답 |

**주의 (결정 필요):**
- 실명 기업의 FTO 결과는 **법적 의견이 아니다.** 공개 산출물·논문에서 실명을 쓸지, 익명화할지는
  기업과의 관계·동의에 달려 있다.
- 기업 포트폴리오가 SDKB 개념 범위(장비 41 · 공정 12 · 세부공정 38 등) 안에 드는지는 수집 후
  IPC·개념 접지율로 먼저 확인한다 — 범위 밖이면 그것이 **도메인 확장 결손 목록**이 된다.
