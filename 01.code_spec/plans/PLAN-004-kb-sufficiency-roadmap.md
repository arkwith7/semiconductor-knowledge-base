## 1. 순서 — 왜 이 순서인가

```
PLAN-002 (공리의 원천이 있는가)  →  PLAN-001 (T-Box·R-Box·A-Box)  →  make vendor(하류)  →  PLAN-003 (E1–E5, 실행은 하류)
      ↑ 판정 *부분* · 사람 결정          ↑ T-Box 변경은 3단계 별도 승인        ↑ 하류 §2.1 새 사전등록
```

1. **PLAN-002 가 먼저다.** PLAN-001 §1.2 의 T-Box 모듈은 **채울 것이 없으면 빈 스키마**다.
   PLAN-001 자신이 머리말에 *"PLAN-002 의 착수 판정이 이 계획의 선행 조건"* 이라고 적었다.
2. **PLAN-001 이 그 다음이다.** 캔 공리를 어느 T-Box·R-Box 에 앉힐지가 여기서 정해진다.
   **`inverseOf`·`propertyChainAxiom`·`disjointWith` 가 0 인 상태를 벗어나는 것이 C-2 의 정의다.**
3. **PLAN-003 은 마지막이다.** 추론이 태스크 응답에 도달하는지(C-5)는 **자원이 바뀐 뒤에만**
   물을 수 있다. 실행은 하류 하네스에서, 판정은 하류 사전등록 아래에서 난다.

**병렬 가능한 것은 없다.** 셋은 서로의 입력이다.

> **보정 (2026-09-05 · [PLAN-005](PLAN-005-prior-art-tool-qualification.md) §6).** 위 문장은
> **PLAN-001·002·003 사이의 관계**에 대한 것이며, 그것은 유지된다. 다만 **진단과 기준선 측정은
> 셋 중 어느 것의 입력도 아니므로 병렬로 진행한다** — PLAN-005 단계 1(V1–V4 기준선)은 읽기
> 전용이고 PLAN-002 의 `Prec` 을 기다리지 않는다. `Prec` 은 **PLAN-001 착수(공리 신설)** 의
> 선행 조건이지 측정의 선행 조건이 아니다.
>
> **확정 (2026-09-05 · 사용자 승인).** 이 보정이 **채택됐다.** 이 문서의 *"병렬 가능한 것은
> 없다"* 는 **PLAN-001·002·003 사이에만** 적용되며, **실행 순서의 정본은
> [PLAN-005 §6](PLAN-005-prior-art-tool-qualification.md) 이다** — 단계 1(V1–V4 기준선) ·
> 2(통지서 인용 해소) · 3(`Prec` 산출)은 **병렬로 간다.** 두 문서의 어긋남은 이 문단으로 닫는다.

## 2. 단계 0 — PLAN-002 의 착수 판정을 확정한다 (사람 결정 🛑)

**현 판정은 *부분* 이며 그 이유는 하나다 — `Prec` 미산출**(PLAN-002 §13 · §19.1).
주 문턱 둘은 교정 후 충족됐다.

| 판정량 | 교정 후 | 문턱 | |
|---|---:|---:|---|
| `P_uniq` | 3,044 | ≥ 400 | 충족 |
| `Q_cov` | 56.5 % | ≥ 0.50 | 충족 |
| `C_conf` | 1,249 | ≥ 100 | 충족 |
| **`Prec`** | **미산출** | — | **이것이 *부분* 의 유일한 원인** |

**결정해야 하는 것.** ① `Prec` 을 재고 그 값으로 완전 판정을 낼 것인가, 아니면 ② *부분* 인 채로
PLAN-001 로 넘어가되 **공리를 `provisional` 등급으로만 싣고** 정밀도 미측정을 자원 카드에
명시할 것인가.

**권고는 ①이다.** 정밀도를 모르는 공리를 T-Box 에 넣으면 하류에서 **자원 결함과 방법 실패가
다시 구분되지 않는다** — 그것이 이 프로젝트에서 반복된 가장 비싼 실패다(하류 §0.1).
`Prec` 표본 채점은 사람 2인 독립 코딩이며 **κ 와 합의율을 동반한다**(하류 §1-12).

> **결정 (2026-09-05 · 사용자 승인) — ①이다.** `Prec` 을 산출하고 그 값으로 **완전 판정**을
> 낸다. 공리를 `provisional` 등급으로만 싣는 ②는 채택하지 않는다.
> **다만 이 산출은 단계 1·2 를 막지 않는다** — §1 확정대로 **병렬**이다. `Prec` 이 선행 조건인
> 것은 **단계 4(공리 신설)** 뿐이다.
> **문턱은 승인 커밋 `15a9ae8` 의 `Prec ≥ 0.60` 그대로이며 한 자리도 바꾸지 않는다**(§1-2).
> `Prec` 이 미달하면 PLAN-002 는 *중단* 이고, **그 판정을 숨기지 않는다**(§5 위험표).

## 3. 단계 1~3 — 종료 조건을 결과 보기 전에 적는다

**아래는 문턱이 아니라 *종료 조건의 형태*다.** 실제 수치 문턱은 각 계획의 **3단계 설계에서
결과를 보기 전에 동결**한다(§2 3단계). 여기서 수를 정하지 않는 이유는, 지금 정하면 그것이
근거 없는 앵커가 되기 때문이다.

| 단계 | 계획 | 종료 조건의 형태 | 확인 방법 |
|---|---|---|---|
| **1** | PLAN-002 | `Prec` 이 산출되고 κ 가 보고됨 · 판정이 *충족* 또는 *중단* 으로 확정 | 계수 리포트 (`01.code_spec/reports/`) |
| **2** | PLAN-001 §1.2·§1.3·**§1.9** | **C-2 의 정의**: `inverseOf`·`propertyChainAxiom`·`disjointWith` 가 각 0 을 벗어나고, **각 공리가 어느 CQ 또는 어느 태스크 경로에 쓰이는지 기계로 확인**됨 — 쓰이지 않는 공리는 넣지 않는다. **판정 공리와 후보 생성 공리를 구분해 적는다**(§1.9) | HermiT 일관성 + CQ 스위트 + **공리 단위 절제**(PLAN-005 §5 V1) |

| **4** | (하류) `make vendor` | 스냅샷 sha256 변경 → **하류 §2.1 새 사전등록 동결** 🛑 | `PROVENANCE.json` |
| **5** | PLAN-003 | **C-5 의 정의**: 추론으로 생긴 경로가 태스크 응답에 도달함이 E1 `SemanticPathRecall` 로 확인됨 | 하류 하네스 |

### 3.1 반드시 함께 재는 것 — 자원 지표만으로 종료를 선언하지 않는다

**하류 §0.1 이 못박은 것을 그대로 적용한다.** 각 단계의 종료 조건에 **하류 태스크 지표를
최소 1개** 건다. 자원 지표는 *수정이 됐는지*, 하류 지표는 *그 수정이 쓸모가 있었는지* 를 잰다.

**이 규칙이 없어서 실제로 그런 일이 났다** — 자원 지표를 2.4배 개선한 변경이 검색 층에서
거부됐다(하류 EP3). **공리를 넣어도 같은 일이 날 수 있고, 그때 그것이 결과다.**

### 3.2 이식성 종료 조건 — 단계 2 에 붙는다 (2026-09-05 · 사용자 승인 · 안 C′-full)

**C-1~C-7 은 하류가 정식화한 것이므로 조건을 새로 추가하지 않는다.** 대신 **단계 2(PLAN-001
§1.2·§1.3·§1.9)의 종료 조건에 이식성 불변식을 건다** — T-Box 를 세우는 그 커밋이 아니면 세울
수 없기 때문이다.

| 단계 | 추가되는 종료 조건 | 확인 방법 |
|---|---|---|
| **2** | `sdkb-priorart-core.ttl` 에 **도메인 IRI 0건 · 관할 IRI 0건** · `pa:underJurisdiction` 없는 `MinedAxiom` **0건** | **CI 불변식**(PLAN-005 §5 V6(a)) · SHACL |
| **6 이후 (신설 8·9)** | **V6b** US 종이 이식에서 core 변경 0줄 · **V6a** 바이오 실물 이식에서 L1 변경 라인수 보고 | PLAN-005 §5 V6 · §6 단계 8·9 |

**왜 단계 2 인가.** 슬롯을 파는 것은 T-Box 설계 시점의 결정이고, TTL 이 발행되어 하류가 vendor
한 뒤에는 IRI 변경이 §0 계약 위반이 된다. **CI 불변식을 나중에 붙이면 이미 오염된 core 를
통과시키게 된다.**

**§1 의 순서는 바뀌지 않는다** — 단계 8·9 는 단계 7 뒤에 서고, 8 이 9 보다 싸다.

## 4. 비목표

1. **C-4(태스크별 외부 정답)를 만들지 않는다.** 전문가 매칭·기술예측의 정답은 **온톨로지 밖에서
   와야 한다**(전문가 패널 판정 등). 합성 A-Box 에서 정답을 파생하는 설계는 쓰지 않는다 —
   순환이다(하류 §0.0.3).
2. **전문가 매칭·기술예측 뷰의 A-Box 를 이번에 채우지 않는다.** 이 로드맵은 **선행기술 뷰 한정**이다.
3. **하류 코드·판정·수치를 바꾸지 않는다.** 상류가 바꾸는 것은 자원뿐이고, 하류는 얼린 스냅샷을
   읽는다. 기존 판정은 **소급 수정하지 않는다.**
4. **공리를 튜닝하지 않는다.** 하류 결과를 본 뒤 공리를 더하거나 빼면 그것은 §1-2 위반이다.
   더 넣고 싶으면 **새 사전등록 아래 새 실험**이다.
5. **어휘를 발명하지 않는다.** 새 술어가 필요하면 3단계에서 별도 승인 — **하류 소비자가 깨진다**(§0).

## 6. 승인 요청 사항 — **세 건 모두 승인됨 (2026-09-05)**

> **승인 기록.** 아래 셋은 사용자 승인으로 닫혔다. ①은 이 문서 머리말과 README 에, ②는 §2 의
> 결정 블록에, ③은 §3 표 단계 2 에 각각 반영돼 있다. **여기에 더해 §3.2(이식성 종료 조건)와
> §1 의 병렬 확정이 같은 날 승인됐다.** 남은 🛑 는 **각 계획의 3단계(설계) 별도 승인**이다.

1. **PLAN-001·002·003 의 지위를 "후속 논문의 착수 조건"에서 "하류 현 논문의 선행 조건"으로
   올리는 데 동의하는가.**
2. **단계 0 의 권고 ①(`Prec` 산출 후 완전 판정)에 동의하는가.** ②를 고르면 공리는 `provisional`
   등급으로만 실린다.
3. **C-2 의 종료 조건을 "공리 개수"가 아니라 "공리↔소비자 대조"로 두는 데 동의하는가** —
   쓰이지 않는 공리는 자원 지표만 올리고 태스크에는 비가시다. 그것이 하류가 이미 실측한 실패다.
